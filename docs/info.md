## How it works

Status (2026-10-17): core v0.1 plus the 512x16 SRAM instruction memory (branch `sram-imem`, hardening in CI), and on branch `protocol-fw` (off `sram-imem`, no RTL change, not merged) the protocol firmware described under "Protocol firmware" below: a UART receiver, an SPI master (modes 0-3) and an I2C master, each tested on the chip RTL against a reference model written from the protocol definition. The chip is a small deterministic CPU (`pe_core`) built for reading pins, writing pins, counting cycles and hitting exact timing, plus a timebase counter, a GPIO block, two host/core data FIFOs and an instruction memory, all wired together and loaded/controlled over a host SPI port (`pe_host_spi`). Data flow at reset: the host writes a program into the instruction memory over the SPI port, then starts the core; each cycle the core fetches from the instruction memory, executes (ALU, branches, pin reads/writes, waits keyed off the free-running timebase, or a push/pop of a host FIFO), and any pin writes go out through the GPIO block, which also synchronises pin reads. The host can read back status, GPIO and popped FIFO words at any time over the same SPI port, whether or not the core is running.

```
host (SPI) --> pe_host_spi --> pe_imem (512x16 SRAM)         pe_timebase (T, free-running)
                    |                |                               |
                    |                v                               v
                    +----------> pe_core  <---- h2c/c2h pe_fifo ---- (host data queues)
                                     |
                                     v
                                 pe_gpio ---> uo_out[6:0], uio_out/uio_oe[7:0]
                                     ^
                                     | (synchronised)
                          ui_in[3:0], uio_in[7:0]
```

The instruction set (`isa/isa.yaml`, the single source of truth) generates the assembler, the Python reference simulator's decode table, the Verilog decode constants (`src/isa_defs.vh`) and the generated reference below (`docs/isa.md`). `tools/gen_isa.py --check` (run in CI) pins the enumerations, the mnemonic table and the reference to that file; the instruction field positions in `src/pe_core.v` are hand-typed, and their agreement with the ISA is checked by the differential fuzzer (RTL against the Python model, `test/test_diff.py`, also run in CI). Sixteen instruction classes are encoded: fourteen implemented (miscellaneous, immediate loads, ALU, add-immediate, pin set/clear/toggle/output-enable, register-driven pin writes (`SETR`), pin/register reads, waits, timebase read/write, conditional branches, jump/call, pin-gated and flag-gated branches, host-FIFO push/pop) and two reserved. Waits target the timebase (exact tick), a pin level or edge, or a status flag, the latter two with a bounded 16-bit timeout. Every instruction is one cycle except the WAIT class; branches, `JMP`, `CALL` and `RET` have one delay slot. Full mnemonic table, field layouts, symbol tables and semantics: [docs/isa.md](isa.md). The lane class (`LCFG`/`LOUT`/`LIN`/`LARM`/`LCRC`/`LTS`, programmable pin engines for line coding, shifting and CRC) is reserved in the ISA but not yet implemented -- see `PLAN.md`'s decision log for the next plan.

Deadlines are wrap-safe: `WAITT Rn` completes in the first cycle in which bit 15 of the 16-bit difference `T - Rn` is 0. A deadline up to 32,768 ticks ahead of `T` stalls and completes exactly in the cycle `T == Rn`; one that has already passed (up to 32,767 ticks behind -- an overrun loop body, or RUN held low across it) completes at once, in its first cycle or in the first cycle after RUN returns; either way the flags are left untouched. Keep deadlines less than 32,768 ticks ahead of `T` and use the prescaler for longer intervals: a deadline 32,769 to 65,535 ticks ahead is indistinguishable from one that has passed and completes at once. The timed waits (`WAITP`, `WAITF`) keep an exact equality compare: they capture `T + timeout` when they start and time out in the cycle `T` equals it, which is what allows the full 65,535-tick timeout (`Rt = R0`).

The instruction memory is 512 x 16 bits, one IHP single-port SRAM macro (`RM_IHPSG13_1P_512x16_c2_bm_bist`): `WRITE_IMEM` addresses and jump/call targets are taken modulo 512, so a program must fit in 512 words (`tools/asm.py` refuses larger ones). It has no reset -- a word the host never wrote holds a random value on silicon -- so load all 512 words (zero-filling the unused ones) before starting the core. The macro has one port, shared between the core's fetch and the host's writes: a `WRITE_IMEM` word that arrives while the core is active (running, including stalled in a wait) is dropped and recorded in `READ_STATUS` bit 5 until the next `WRITE_CTRL` reset; pause the core (RUN low and `WRITE_CTRL` run=0: either one holds it active) or let it `HALT` before loading.

## Host loader protocol

Mode-0 SPI slave, MSB first, one command byte followed by its payload; CS_n must stay asserted through the SPI clock edge that samples a byte's last bit. SCK must run at clk/16 or slower.

| Cmd | Value | Payload (host -> chip) | Response (chip -> host, if any) |
|---|---|---|---|
| `WRITE_IMEM` | 0x01 | start address (2 bytes, hi then lo; the memory uses the low 9 bits, so addresses alias modulo 512) then instruction words (2 bytes each, hi then lo); address auto-increments per word | -- |
| `WRITE_CTRL` | 0x02 | 1 byte: bit0 = run, bit1 = reset (restarts PC at 0) | -- |
| `READ_STATUS` | 0x03 | -- | 4 bytes: status (bit0 halted, bit1 running, bit2 h2c-FIFO valid/non-empty, bit3 c2h-FIFO empty, bit4 h2c-FIFO full, bit5 imem write dropped), PC[9:8], PC[7:0], flags[2:0] (bit0 = Z, bit1 = C, bit2 = TO) |
| `PUSH_FIFO` | 0x04 | 2 bytes (hi, lo): word pushed to the host->core FIFO (dropped if full) | -- |
| `POP_FIFO` | 0x05 | -- | 2 bytes (hi, lo): word popped from the core->host FIFO (0 if empty) |
| `READ_GPIO` | 0x06 | -- | 5 bytes: `ui_in`, `uio_in`, `{1'b0,uo_out}`, `uio_out`, `uio_oe` (all synchronised snapshots) |
| `WRITE_PRESCALE` | 0x07 | 1 byte: timebase divider -- the timebase T ticks once every (value + 1) clock cycles, so 0 (the reset value) means a tick every clock cycle | -- |

Status bit4 (h2c-FIFO full) lets the host poll before a `PUSH_FIFO` instead of racing a silent drop; the FIFO is 4 entries deep.

`ui[7]` (RUN) is also a direct, asynchronous top-level input: asserting it starts the core exactly like `WRITE_CTRL`'s run bit, and either one holds the core active until deasserted. Because `ui[7]` is asynchronous, it passes through the GPIO block's two-flop input synchroniser before reaching the core's own registered RUN sample -- three clock cycles total from a RUN pin transition to the first instruction executing (2 sync flops + 1 core RUN register). `WRITE_CTRL`'s run bit is already a register in the clock domain and takes effect one cycle sooner (both latencies are pinned by `test/test_host.py::run_latency_pin_three_cycles_ctrl_two`). Deasserting RUN (or `WRITE_CTRL` run=0) pauses the core where it is -- registers, PC and any wait in progress are kept -- and reasserting it resumes; `WRITE_CTRL` bit1 restarts at PC 0 and is the only way to restart a core that has executed `HALT` (RUN alone does not). `tools/host.py` provides Python encoders for `WRITE_IMEM`, `WRITE_CTRL` and `WRITE_PRESCALE` (`encode_write_imem`, `encode_write_ctrl`, `encode_write_prescale`; the read and FIFO commands are sent as plain byte strings) plus a cocotb `SpiMaster`, both used throughout `test/test_host.py`.

Caveats worth knowing when driving the port:

- `READ_STATUS` returns the PC in two bytes read 16 SCK edges apart; while the core is running the two halves can come from different cycles, so the PC is only coherent when the status byte says halted (or the core is paused).
- The timebase `T` free-runs from reset, whatever the core does. While RUN is low (or the core is halted) a wait in progress keeps its deadline but `T` keeps counting. A `WAITT` whose deadline passes meanwhile completes in the first cycle after RUN returns, provided `T` is then at most 32,767 ticks past the deadline (`test/test_host.py::run_low_across_deadline_resumes_immediately`); after a longer pause the deadline can count as ahead again -- only the 16-bit difference `T - Rn` is compared -- and the `WAITT` then waits up to 32,768 ticks for `T` to reach it (32,768 ticks is about 655 us at 50 MHz with prescale 0, about 168 ms with prescale 255). A timed wait (`WAITP`/`WAITF`) whose captured timeout passes meanwhile times out only when `T` comes round to it again, up to 65,536 ticks later, so do not pause a core across a timeout it needs.
- `WRITE_PRESCALE` takes effect on the next clock. If the new value is below the prescaler's current count, that one tick interval stretches to as many as 256 clocks (the 8-bit counter runs on to 255 and wraps before matching the new value); later ticks are exact.

## Protocol firmware

Protocols are implemented in firmware: the core reads and writes the protocol pins against exact timebase deadlines, and each firmware program is tested on the chip RTL against a reference model written from the protocol's own definition (not from the firmware). Protocol pins are `ui[3:0]` (inputs), `uo[6:0]` (outputs) and `uio[7:0]` (bidirectional); `ui[7:4]` and `uo[7]` belong to the host port.

| Signal | Pin | Direction |
|---|---|---|
| UART TX (`firmware/uart_tx.s`) | `uo[0]` | out |
| UART RX (`firmware/uart_rx.s`) | `ui[0]` | in |
| SPI SCK / MOSI / CS_n | `uo[1]` / `uo[2]` / `uo[3]` | out |
| SPI MISO | `ui[1]` | in |
| I2C SDA / SCL | `uio[0]` / `uio[1]` | open-drain: `uio_out` bit stays 0, `OE` set = pull low, `OE` clear = released |

**Timing constants.** Each firmware file states the clock it was computed for (50 MHz) in its header comment and keeps every timing constant in one `.equ` block at the top, each with its formula; no timing number appears anywhere else in the file. The block also holds `.equ PRESCALE n`, the `WRITE_PRESCALE` value (one tick = n+1 cycles) the constants assume. The tests read `PRESCALE` from the firmware source (`tools.asm.constants()`) and program it over the host port, so the host side cannot drift from the firmware; nothing else in the block is used by a test: the reference models take their timing from the protocol parameters and `CLK_HZ = 50_000_000`, declared at the top of each test module. Retargeting a firmware to another clock means editing its `.equ` block (values and formulas), `CLK_HZ` in its oracle test module (`tests/test_fw_uart_rx.py`, `tests/test_fw_spi.py`, `tests/test_fw_i2c.py`, which the cocotb suites import), the sentinel mutant text (`MUTANT_BIT`, `MUTANT_HALF`, `MUTANT_Q`, re-chosen so the mutant stays outside the tolerance), the 50 MHz literals in the model self-tests, the measured figures in this section, and `clock_hz` in `info.yaml`; the models and their tolerances follow from `CLK_HZ`. The owner decided on 2026-10-16 to keep 50 MHz (recorded in `sram-imem`'s plan commit 147e69b), so no retargeting is planned. All waits are `SETT`/`ADDT` relative deadlines, since `T`'s value at start is unspecified.

### UART receiver (firmware/uart_rx.s)

8N1 at 115200 baud on `ui[0]`, 36 instruction words. Constants: `PRESCALE 1` (tick = 2 cycles), `BIT 217` (ticks per bit = 50e6 / 115200 / 2), `HALF 108` (ticks from the detected start edge to the middle of the start bit: 108.5 truncated, and the two-cycle edge-detection latency recentres the sample). The firmware waits for the line to be high (idle), then for it to be low (the start bit), as two level waits (`WAITP ... HIGH` then `WAITP ... LOW`, each with the 65,535-tick timeout that simply rearms it): a level wait that rearms still sees a start bit that arrived meanwhile, where an edge wait would miss it, and the idle wait also waits out a break after a framing error. It then samples the middle of the start bit and goes back to waiting if the line is high again (false-start rejection), then samples the eight data bits (LSB first) and the stop bit at the detected edge plus 1.5, 2.5, ... 9.5 bits. Each frame is pushed to the core->host FIFO as one word: `{frame_error[8], data[7:0]}`, bit 8 set when the stop bit read low; read it with `POP_FIFO`. The push does not wait for room: a frame that arrives while the 4-entry FIFO is full is dropped, so the host must drain faster than 11,520 words/s. The push comes 6 to 9 cycles after the ideal stop-bit sample instant (start edge + 9.5 bits) in the test cases (oracle and RTL).

The reference model (`tools/refmodels/uart_rx_ref.py`) generates the line and checks the pushed words. A frame passes when exactly the expected words are pushed, in order, each within [ideal stop sample - bit/8, ideal stop sample + bit/8 + 32 cycles] (the stop sample measured at the nominal baud rate, so this pins the sample instant on every frame). The cases: nominal bytes (0x55, 0x00, 0xFF, 0xAA, 0xA3, back to back); a whole frame at 115200 x (1 - 4 %) and x (1 + 4 %); probe frames, whose data bits and stop bit carry their value only within +-bit/8 of the ideal sample instant and the complement elsewhere (so sampling outside the middle quarter of a bit reads a wrong byte or a false framing error; the stop bit's low tail is a deliberate glitch the receiver must reject, so the model requires at least a quarter bit of idle after a probe frame); a framing error (stop bit low, bit 8 set) followed by a good frame; a 100-cycle glitch (nothing may be pushed) followed by a good frame; a 140,000-cycle idle gap (the idle wait times out once and rearms); a break, the line held low for 20,000 cycles (46 bits) and then a good frame: exactly one word, 0x100, in the normal window measured from the break's first low cycle as if it were a start edge (start + 9.5 bits - bit/8 to start + 9.5 bits + bit/8 + 32, about 4,069 to 4,209 cycles; the model requires a break of at least one frame, 10 bits, so every sample a receiver inside the tolerance takes reads low), then 0x5A, so a receiver that does not wait for the idle line before the next start bit reads the rest of the break as more frames and fails (the oracle test `test_uart_rx_break_fails_without_the_idle_wait` shows it: six words instead of two). On the oracle only, a scan of gaps around 130,871 cycles, where the earlier falling-edge design missed the start bit while its timed-out wait rearmed, checks the level waits do not.

Suite: `test/Makefile.uartrx` (`test/test_uart_rx_fw.py`: `uart_rx_nominal`, `uart_rx_slow_4pct`, `uart_rx_fast_4pct`, `uart_rx_probe`, `uart_rx_framing`, `uart_rx_glitch`, `uart_rx_long_idle`, `uart_rx_break`, and `uart_rx_sentinel_mutant_is_rejected`, which assembles the firmware with `BIT 210` (3 % fast) and requires the model to reject it). Every case also reads the words back over `POP_FIFO` while it runs and checks them against the monitored pushes. The same cases run on the Python oracle in `tests/test_fw_uart_rx.py`.

### SPI master (firmware/spi_master.s)

SPI master, modes 0-3, SCK 1 MHz at 50 MHz, MSB first, 8 bits per byte; 71 instruction words. Pins: SCK `uo[1]`, MOSI `uo[2]`, CS_n `uo[3]` (active low), MISO `ui[1]`. Constants: `PRESCALE 0` (tick = 1 cycle), `HALF 25` (ticks per SCK half period = 50e6 / 1e6 / 2), `CSLEAD 25` (CS_n low to the first half-step), `CSLAG 25` (last SCK edge to CS_n high for CPHA = 0; CPHA = 1 adds a half period because the byte's deadline has already advanced past its last edge), `CSIDLE 25` (minimum CS_n high between transactions).

| Mode | CPOL (idle SCK) | CPHA | MOSI changes on | MISO/MOSI sampled on |
|---|---|---|---|---|
| 0 | 0 | 0 | falling (trailing) edge; first bit set up before the first edge | rising (leading) edge |
| 1 | 0 | 1 | rising (leading) edge | falling (trailing) edge |
| 2 | 1 | 0 | rising (trailing) edge; first bit set up before the first edge | falling (leading) edge |
| 3 | 1 | 1 | falling (leading) edge | rising (trailing) edge |

The host drives it byte by byte through the FIFOs. Command word (`PUSH_FIFO`): bits 7:0 the byte to send, bit 8 LAST (raise CS_n after this byte), bits 10:9 the mode {CPOL, CPHA}. CPOL is applied when a transaction starts (CS_n high when the word is popped), CPHA is read from every word, so keep the mode constant within a transaction. Result word (`POP_FIFO`): bits 7:0 the byte read on MISO during that byte, one per command, pushed after the byte's last edge; the firmware retries the push until the FIFO has room (a timed `WAITF TXE` in a retry loop), so nothing is dropped however long the host leaves the FIFO full (`tests/test_fw_spi.py::test_spi_result_push_waits_for_room` holds it full for 70,000 cycles and also shows the single-wait version losing a word). On the first command of a transaction the firmware sets SCK to the CPOL level, lowers CS_n and anchors its deadlines there; every SCK edge is a `WAITT` deadline, so within a byte the edges are exactly `HALF` ticks apart in every mode. Between bytes SCK stays idle until the next command arrives (the firmware re-anchors after each `POP`, so a slow host only lengthens the gap). MISO is read with `IN`, i.e. the pin as it was about two cycles before the sampling edge. Measured on the oracle and the RTL: the first edge comes 52 cycles after CS_n falls in modes 0/2 (MOSI set up 25 cycles before it) and 27 cycles in modes 1/3; CS_n rises 25 (modes 0/2) or 50 (modes 1/3) cycles after the last edge. `uo` resets to 0, so CS_n (`uo[3]`) is low (asserted) from reset until the firmware's first instruction raises it, and SCK and MOSI are low; a slave sees one selected period with no SCK edges before the first transaction. Boards whose slave reacts to CS_n alone should gate CS_n externally.

The reference model (`tools/refmodels/spi_slave_ref.py`) is an SPI slave written from the mode definitions that also judges the master; its tolerances come from the nominal period P = 50 cycles (H = 25), never from the firmware: SCK at CPOL when CS_n falls, between bytes and when it rises, and at most one SCK change (the CPOL switch) while CS_n is high; first edge at least H - 2 after CS_n falls, last edge at least H - 2 before it rises, CS_n high at least H - 2 between transactions; every edge-to-edge interval within a byte H +- 1, between bytes at least H - 1; MOSI stable from P/4 before to P/4 after every sampling edge; a whole number of bytes (16 edges each) per transaction, and a transaction still open at the end of a run or one with no SCK edges is a violation. It drives MISO MSB first, each bit valid 5 cycles after its shifting edge; in the window tests a bit is valid only within +-P/8 = 6 cycles of its predicted sampling edge and the complement elsewhere, so a master that samples on the wrong edge reads a wrong byte (a CPHA=0 byte's first bit, whose sampling edge follows a host-paced gap, is windowed on one side only: valid from its shifting event until the sampling edge plus 6 cycles, then the complement).

Suite: `test/Makefile.spifw` (`test/test_spi_fw.py`: `spi_mode0` .. `spi_mode3` (bytes 0x83, 0x1C, 0xA6 out and 0xC1, 0x0F, 0x9A back in one transaction, none of them the same bit-reversed, MISO window on), `spi_mode_change` (a mode-0 transaction then a two-byte mode-3 one), `spi_single_byte` (mode 2), `spi_late_words` (3,000 cycles between commands), and `spi_sentinel_mutant_is_rejected`, which assembles the firmware with `HALF 27` (an 8 % slow SCK) and requires the model to reject it). Each case pushes its commands over `PUSH_FIFO`, reads the results back over `POP_FIFO` while it runs and checks them against the monitored pushes, and checks that every edge interval within a byte is exactly `HALF`. The same cases run on the Python oracle in `tests/test_fw_spi.py`, which also tests the model itself on synthetic master traces.

### I2C master (firmware/i2c_master.s)

I2C master, standard mode (UM10204), 7-bit addressing, single master; 167 instruction words. Pins: SDA `uio[0]`, SCL `uio[1]`, open drain: the firmware never sets `uio_out`, `OE 1` pulls a line low and `OE 0` releases it (external pull-ups; the bus level is read back on `uio_in`). Constants: `PRESCALE 0` (tick = 1 cycle), `Q 128` (a quarter of the SCL period = ceil(50e6 / 100e3 / 4) + 3 ticks, 2.56 us), `TRISE 53` (ceil(1000 ns x 50 MHz) = 50 ticks, the standard-mode rise-time limit, + 3 for the output register and the input synchroniser: the longest a released SCL may take to read back high before the firmware calls it a stretch). Every step sits on a quarter-period grid: SCL low and high nominally 2Q each, tSU;STA = tHD;STA = tSU;STO = tBUF = 2Q, SDA changed Q after SCL falls (tHD;DAT = tSU;DAT = Q). The measured period is 4Q + 11 = 523 cycles (10.46 us, 95.6 kHz), not 4Q: the grid re-anchors at the observed SCL rise, which comes about 11 cycles after the release deadline (pin write, input synchroniser, `WAITP`), so tHIGH = 2Q + 9 and tLOW = 2Q + 2. A bus rise time adds to tLOW only: at the 1 us standard-mode maximum the period is 573 cycles (11.46 us, 87.3 kHz).

The host drives it one byte per command. Command word (`PUSH_FIFO`): bits 7:0 the byte to write, or for a read the ACK control (bit 0 = 1: answer the byte with NACK, 0: ACK); bit 8 START (a START, or a repeated START, before the byte); bit 9 STOP (a STOP after the byte); bit 10 READ (receive a byte instead of writing one). The address byte is an ordinary write of `addr << 1 | R/W` with START set. Result word (`POP_FIFO`), one per command, pushed when the command is done (the firmware retries the push until the FIFO has room, so nothing is dropped however long the host leaves it full): bits 7:0 the byte written (echo) or read (the firmware takes the command's byte at the `POP`, so a command that times out in its START reports its own byte, not the previous result); bit 8 NACK (the written byte was not acknowledged); bit 9 TIMEOUT; bit 10 STRETCHED. Between commands the firmware holds SCL low in the middle of a transaction (so a slow host only stretches the clock) and leaves both lines released when idle; it re-anchors its deadlines after every `POP`. Host misuse is not caught: a command without START on an idle bus produces a spurious START or STOP condition; READ with START reads with no address byte; there is no bare STOP command and no bus-clear after a TIMEOUT -- the host sends a new START.

Clock stretching: wherever the firmware releases SCL (before a written bit, a read bit, a START or a STOP) it waits up to `TRISE` ticks for the line to read back high (`WAITP` with a timeout). A slave is reported as stretching only if SCL is still low 53 ticks, 1.06 us, after the master released it -- the standard-mode rise-time limit plus the chip's read-back latency; the high period is always timed from the observed rise. So a bus with any legal rise time (up to 1 us) never sets STRETCHED by itself; on a stretch the firmware sets STRETCHED on the current command's result and keeps waiting for the rise, and tHIGH and the period hold with or without stretching. If SCL stays low for 65,535 ticks (1.3 ms) the firmware releases both lines, abandons the rest of the command (including a requested STOP) and reports TIMEOUT (with NACK if it was already known, without STRETCHED, which means a stretch that ended in time); the next command may start a new transaction with a START once the slave lets go.

Measured on the oracle with an ideal pull-up (cycles at 50 MHz; the RTL gives the same byte timing; the standard-mode limit in brackets): tLOW 258 (>= 235; 282 for the first bit after a command boundary, 285 after a NACKed byte), tHIGH 265 (262 for the bit after a stretch; >= 200), period 523 = 10.46 us, 95.6 kHz (>= 500; at most 550, at a command boundary after a NACKed byte), tSU;STA 265 for a repeated START (>= 235), tHD;STA 256 (>= 200), tSU;STO 265 (>= 200), tBUF 792 (>= 235), SDA hold after SCL falls 128-130 (<= 172), SDA setup before SCL rises at least 128 for the master (>= 13). One byte takes 4,731 cycles from ACK to ACK (nine 523-cycle bits plus the command boundary); a command with START, one byte and STOP about 6,300 (6,275 to the result of `addr_nack`). With a 50-cycle (1 us) rise on both lines (`rise_time`): tLOW 308, tHIGH 265, period 573, tSU;STO 315, 5,181 cycles from ACK to ACK, no violation and no STRETCHED. (At that rise the master's SDA change, Q = 2.56 us after its SCL fall, reaches the high level 3.56 us after the fall, past tVD;DAT = 3.45 us; its setup before the next rise is still at least 128 cycles, 2.56 us, because the high period is timed from the observed rise.)

The reference model (`tools/refmodels/i2c_slave_ref.py`) is an I2C slave written from the bus definition that also judges the master. It computes the wired-AND bus from the master's pull-downs (`uio_oe & ~uio_out`) and its own and drives `uio_in` with it, so the suite needs no Verilog testbench of its own. It decodes START and STOP (only between bytes), bits on SCL's rising edge and nine-bit bytes, and checks on the bus, in cycles from `CLK_HZ` (never from the firmware): period >= 10 us, tLOW >= 4.7 us, tHIGH >= 4.0 us, tSU;STA >= 4.7 us, tHD;STA >= 4.0 us, tSU;DAT >= 250 ns, tHD;DAT <= 3.45 us (checked on every master SDA change while SCL is low, the first bit after a START included; exempt are only the master's first change after an ACK bit, where it holds SCL low for its host, and changes while the slave stretches), tSU;STO >= 4.0 us, tBUF >= 4.7 us; any other SDA change while SCL is high, a master line driven high (`uio_oe & uio_out`: the open-drain contract), a byte cut short and a transaction left without a STOP are violations too. As a slave it ACKs its own address (0x50) in either direction and gives no response to others, stores written bytes, serves read data until the master NACKs, and optionally NACKs data bytes from the n-th on or holds SCL low for a given number of cycles after a byte's ACK bit, recording how long after its release SCL rose on the bus. Sampling-instant check (the I2C counterpart of the SPI MISO window): every bit the slave transmits (read data, its ACK or NACK) is the complement from the cycle SCL falls and the real level only from tVD;DAT = 3.45 us (172 cycles) after the fall, or, while it stretches, from tSU;DAT before it lets SCL go; so a master that samples SDA after the fall, or in the low phase, reads the complement of the bit the slave transmits next, so a late or low-phase sampler is caught wherever two adjacent transmitted bits are equal, and only one that samples while SCL is high reads the right one. An optional rise time (`rise_cycles`) keeps a released line low for that many cycles before it reads high, SDA and SCL alike; every check measures on the bus as returned. The slave's own setup stays legal: 258 - 172 = 86 cycles against the firmware's SCL low (>= 13), exactly 13 after a stretch.

Suite: `test/Makefile.i2cfw` (`test/test_i2c_fw.py`: `i2c_write2` (address 0x50, bytes 0xA5 and 0x3C, STOP), `i2c_read2` (two bytes read, ACK then NACK + STOP), `i2c_write_restart_read` (write a byte, repeated START, read one: the EEPROM pattern), `i2c_addr_nack` (address 0x51, NACK in bit 8), `i2c_data_nack` (the slave NACKs the data bytes), `i2c_stretch` (the slave holds SCL low for 1,000 cycles, 20 us, after the address ACK, before a written bit: the transfer is correct and STRETCHED is set on the next command's result only, not on the one after), `i2c_read_stretch` (the same stretch before the first read bit: STRETCHED on the first read's result only), `i2c_stop_stretch` (a stretch after the data byte's ACK, before the STOP), `i2c_timeout` (the slave holds SCL for 80,000 cycles: TIMEOUT, lines released, no STOP; a START pushed at cycle 90,000 on the oracle (about 96,000 on the RTL, where the host paces it from the previous result), after the slave let go, succeeds with no STRETCHED), `i2c_start_timeout` (the same stretch, but the next command is a repeated START that times out: its result is its own byte 0xA1 with TIMEOUT only), `i2c_rise_time` (the `write2` commands on a bus with the standard-mode maximum rise time, 50 cycles = 1 us, and no slave stretching: no result may carry STRETCHED), and `i2c_sentinel_mutant_is_rejected`, which assembles the firmware with `Q 96` (nominal SCL low 3.84 us, measured period 7.9 us) and requires the model to reject it). `i2c_stretch` runs with a 3-cycle (60 ns) rise time, so the STRETCHED flag is shown to survive a modest rise; the other cases have an ideal pull-up on the RTL, and no result may carry STRETCHED unless the slave stretched. In every stretching case SCL must be high on the bus within the rise time + 10 cycles of the slave's release (after a timeout: the master really let go). Each case pushes its commands over `PUSH_FIFO`, reads the results back over `POP_FIFO` while it runs and checks them against the monitored pushes. The same cases run on the Python oracle in `tests/test_fw_i2c.py`, every case without its own rise time at both 0 and 3 cycles (20 runs), which also tests the model itself on synthetic master traces, shows that the pre-fix single read-back (`DELAY 3` / `BPIN`, five cycles after the release) sets STRETCHED on every result at a 3-cycle rise (`test_i2c_master_single_readback_flags_a_rise_as_a_stretch`), checks tBUF with a STOP followed by a new transaction, holds the result FIFO full until cycle 80,000 (`test_i2c_result_push_waits_for_room`, and the single-wait version losing a word), and runs firmware mutants the model must reject: SDA sampled after the SCL fall, SDA sampled in the low phase, and an abort that holds SCL low.

## How to test

1. Apply the clock and release reset with `ui[7]` (RUN) held low and CS_n high. After reset the core is halted, `uio_oe == 0`, and all outputs are 0 (`test/test_host.py::post_reset_state_and_running_bit` checks this on the pins).
2. Load a program with `WRITE_IMEM` (all 512 words, see above), then start it with `WRITE_CTRL` (run=1) or by raising `ui[7]`. After a `HALT`, restart with `WRITE_CTRL` run=1, reset=1.
3. Observe the protocol pins (`ui[3:0]`, `uo[6:0]`, `uio[7:0]`) driven by the loaded program, and optionally poll `READ_STATUS` / `READ_GPIO` or exchange words with `PUSH_FIFO` / `POP_FIFO`.

Worked example -- `firmware/blink.s` (toggles `uo[0]` every 10 cycles forever):

```
; Toggle uo[0] every 10 cycles forever (period 20 cycles):
; TGL(1) + DELAY 6(7) + JMP(1) + delay-slot NOP(1) = 10 cycles per loop.
.equ HALF 6
top:
  TGL UO, 0x01        ; visible next cycle
  DELAY HALF          ; HALF+1 cycles
  JMP top             ; delay slot below executes
  NOP
```

Assemble it to get the instruction words: `.venv/bin/python tools/asm.py firmware/blink.s` prints the four 16-bit words for PC 0-3, one per line: `4801`, `7206`, `a000`, `0000`.

The exact SPI byte sequence to load and run it (`tools/host.py`'s `encode_write_imem(0, [0x4801, 0x7206, 0xa000, 0x0000])` and `encode_write_ctrl(run=True)`), each row one CS_n-framed transaction, MSB first:

| Step | CS_n | Bytes (hex) | Meaning |
|---|---|---|---|
| 1 | low..high | `01 00 00 48 01 72 06 A0 00 00 00` | `WRITE_IMEM`, start address 0x000, then the 4 program words |
| 2 | low..high | `02 01` | `WRITE_CTRL`, run=1, reset=0 -- the core starts at PC 0 |

After step 2, `uo[0]` toggles every 10 core clocks (20-clock period) indefinitely. `test/test_host.py::datasheet_blink_sequence` exercises this exact sequence end to end in cocotb: it checks the two byte strings above against what `tools/asm.py` and `tools/host.py` produce from `firmware/blink.s`, sends those literal bytes over the SPI pins, and measures the toggle interval on the `uo[0]` pin itself.

## External hardware

None. Loading and control is entirely over the host SPI port on the dedicated pins; any SPI-capable host (including the demo board's RP2040) can drive it. The protocol pins (`ui[3:0]`, `uo[6:0]`, `uio[7:0]`) are free for whatever protocol the loaded firmware implements -- no fixed external hardware is required for the core itself.
