# Academic/Architectural Prior Art — Timing-Predictable and Timing-Instruction ISAs (2026-09-15)

Scope: academic/architectural prior art for timing-predictable ISAs and pin I/O, for the protocol-emulator ASIC (time-triggered core + programmable pin "lanes"; see `competition-brief.md` and `docs/superpowers/specs/2026-09-15-protocol-emulator-design.md`). Complements `verification-novelty.md` (tooling scan) — this is the hardware/ISA lineage. 17 primary documents were opened and read (papers, tech-report PDFs, architecture manuals, datasheets); a few extra facts came from search snippets only, marked as such. PDFs WebFetch couldn't parse were extracted locally with `pypdf`. Uncertain claims are flagged; nothing was fabricated.

## 1. Summary

Every architecture here picks one of two philosophies: **repeatable timing by ISA construction** (PRET/PTARM/FlexPRET's `deadline`/`DU` instructions, XMOS's per-port `SETPT` hardware timers, Propeller's `WAITCNT` accumulate-without-drift idiom — all mechanically identical in spirit to our `ADDT`/`WAITT` loop) or **predictable-but-not-repeatable timing by WCET analysis** (Patmos/T-CREST, which explicitly rejects the PRET philosophy and ships a fixed hardware Ethernet MAC rather than firmware). None of the timing-instruction machines (PRET family, XS1) ship dedicated line-coding/CRC serialization hardware — that only appears in RP2040 PIO and Propeller 2 smart-pins/streamer, and even there no CRC/bit-stuffing hardware exists, no formal semantics paper was found for either, and Propeller's documented `WAITPEQ`/`WAITPNE` hang risk is never formally closed anywhere. Our bet — provably-timed scalar deadline ISA + CRC/line-coding pin engines + a from-scratch formal-proof artifact — combines pieces that exist separately across five architecture families but not together, and not formally verified as a unit, anywhere in this literature.

## 2. Architectures and papers

**1. PRET / "The case for the precision timed machine" (Edwards & Lee, DAC 2007 / UCB/EECS-2006-149).** Position paper, not a design: argues WCET-based real-time computing is broken by modern pipelines/caches, proposes ISA-level cycle-accurate timers, scratchpad memory instead of caches, thread-interleaved pipelines. No concrete I/O — lists "high-precision I/O" as an open problem. *For us*: validates "timing as ISA concept" at the top level but gives nothing on pins, which is exactly where we diverge.

**2. Ip & Edwards, "A Processor Extension for Cycle-Accurate Real-Time Software" (EUC 2006) — PRET's direct deadline-instruction precursor.** 25 MHz MIPS-like FPGA core with `dead T,Rs`/`deadi T,imm`: a 16-bit down-counting timer blocks the thread until zero, then reloads synchronously. Demonstrated as a VGA text controller and a UART auto-baud receiver, both far shorter than VHDL equivalents. I/O is plain memory-mapped registers, no serialization hardware. Noted limitation: doesn't fit a multitasking OS (timers need save/restore on context switch). *For us*: closest literature match to our `ADDT`/`WAITT` idiom; we generalize it (16 regs, 16-bit deadline arithmetic, no lanes in theirs).

**3. PTARM / Lickly, Liu, Kim, Patel, Edwards, Lee, "Predictable Programming on a Precision Timed Architecture" (CASES 2008 / UCB/EECS-2008-40).** SPARC extension adding the deadline instruction to a six-stage thread-interleaved pipeline (one hardware thread per pipeline stage, no bypass/hazard logic needed). Each thread gets a 64 KB 1-cycle scratchpad plus shared 16 MB main memory via a fixed round-robin "memory wheel" (explicitly Propeller-hub-inspired): 13-cycle access window in a 78-cycle wheel, worst case 77-cycle wait, handled deterministically via pipeline "replay." I/O is a memory-mapped UART only. *For us*: confirms the deadline instruction works with real multithreading and a fixed-window arbiter; reinforces that nobody in this line built serialization hardware.

**4. FlexPRET (Zimmer, Broman, Shaver, Lee, RTAS 2014 / UCB/EECS-2013-172).** RISC-V, 5-stage, fine-grained multithreaded. Threads are Hard-Real-Time (HRTT, fixed slot) or Soft-Real-Time (SRTT, round-robin on leftovers) via two control registers. Timing ISA: `GTH`/`GTL` read a 64-bit ns clock; **`DU r1,r2`** (delay-until, absolute time) blocks by *replaying* the instruction, and — unlike PTARM — wasted cycles are reclaimed by other SRTTs; **`EE r1,r2`** (exception-on-expire) arms a timer interrupt at an absolute deadline; `DE` deactivates it. Scratchpad-based, no caches. Limitation (README): RISC-V privileged-spec port incomplete. No pin hardware. *For us*: `DU`/`EE` are close analogues of our `WAITT`/deadline arithmetic, but reclaim idle cycles across threads — an idea we don't use since our core is single-threaded.

**5. InterPRET (Jellum et al., CPS-IoT Week 2023) — FlexPRET successor.** Couples FlexPRET cores via the S4NOC network-on-chip for "end-to-end time-predictable" multicore. *Uncertain*: only the abstract page was accessible (ACM full text 403, MIT DSpace PDF 405); numbers beyond the abstract unverified. *For us*: closest precedent for the design doc's "second core, shared instruction memory" v1 idea, at far larger scale than our ~24K-cell budget.

**6. Patmos / T-CREST (Schoeberl et al., J. Syst. Archit. 2015; Patmos Reference Handbook).** The opposite philosophy: dual-issue static-schedule RISC with a method cache and split stack/data caches, built for WCET *analyzability* (via `aiT`/`platin`) rather than repeatable hardware timing. Handbook quote: "the main difference between our proposal and PRET is that we focus on time predictability and PRET on repeatable timing... PRET is essentially static, resulting in a higher implementation cost." Patmos does have a memory-mapped **"Deadline" device** (`0xf0030000`, load stalls the pipeline until a countdown hits zero) — the same idea as Ip & Edwards, demoted to an optional peripheral. I/O is memory-mapped: a minimal polled UART, and a **fixed hardware EthMac block** for Ethernet — not firmware. Multicore uses the Argo NoC (TDM, no buffering) for predictable messaging. *For us*: confirms "firmware Ethernet" is unclaimed — the one architecture here with 10BASE-T-class capability does it with a fixed MAC, the opposite of our design principle 3.

**7. XMOS XS1 ("The XMOS XS1 Architecture," manual X7879A) + XC "timed output on a port" doc.** Threads scheduled round-robin per XCore (1/n cycle fairness, not cycle-exact). The relevant mechanism is **per-port hardware timing**: each port has its own timer, clocked by the reference clock or a programmable `clock` block (`SETCLK`); `SETPT p,t` arms a port so the transfer register moves to/from pins exactly when the port's own timer matches `t`. Input ports also support a `condition` (edge/value match) that timestamps the sample and blocks the thread until met. XC syntax confirmed from the official doc: `toggle_port @ count <: 1;`. *For us*: XS1 solves per-pin timing with **hardware timers distributed to every port**, decoupled from CPU timing — the mirror image of our single global deadline register (`T`) driving shared lanes. No CRC/line-coding hardware; proprietary toolchain.

**8. Parallax Propeller 1 (P8X32A datasheet Rev 1.4).** Eight cogs share 32 pins and a round-robin "hub" (16-cycle access period — the acknowledged inspiration for PTARM's memory wheel, per PTARM's own paper). **`WAITCNT D,S`** — wait until free-running `CNT`==`D`, then `D+=S` — is exactly our no-drift `ADDT`/`WAITT` idiom. `WAITPEQ`/`WAITPNE` block until pins (mis)match a mask; `WAITVID` hands pixels to a video generator. Documented risk: `WAITPEQ`/`WAITPNE` have no built-in timeout and can hang a cog forever. No line-coding/CRC hardware. *For us*: our `WAITP` already has an optional timeout register — we already fix Propeller 1's best-documented footgun.

**9. Parallax Propeller 2 (p2docs.github.io + Silicon Doc).** Closest single prior-art match to our "lanes." Each of 64 pins has an independent **smart pin** (configured via `WRPIN`/`WXPIN`/`WYPIN`) in one of ~30 modes: NCO frequency/duty, PWM (triangle/sawtooth/SMPS), sync/async serial TX/RX (hardware UART-style per pin), quadrature/edge counting, 8-bit DAC/ADC, paired USB transceiver. A separate **Streamer** does NCO-clocked DMA-like transfer between hub memory and pins/DACs (`XINIT`/`XCONT`/`XZERO`/`XSTOP`, deterministic 2-cycle latency). No CRC/bit-stuffing hardware anywhere; no published formal-verification literature found. *For us*: architecturally close to our lane concept but stops short of CRC/line coding — a concrete differentiator for USB/Ethernet.

**10. RP2040 PIO — academic use as a precision pulse generator (Starkey, Turnbaugh, Miller, LeBlanc, Meyer, arXiv:2406.17603, 2024).** Not a formal-methods paper — no true formal/academic analysis of PIO semantics was found despite a targeted search (a real gap, see §4). Empirical use instead: "Prawnblaster"/"Prawn-DO" pulse generators reporting **7.5 ns resolution, 37.5 ns min pulse width**, waits bounded below by the PIO's minimum per-instruction cost (5 cycles, tightest loop) and above by 2³²−1 cycles. Determinism comes purely from fixed per-instruction cycle cost, not a proven model. *For us*: confirms PIO-class devices are already used exactly where our chip is aimed, and that no formal timing-correctness proof exists for one (novelty #2).

**11. TI Sitara PRU (cited directly in the competition brief) — academic use (Fedrizzi & Soria, arXiv:1504.07024, 2015).** BeagleBone PRU as a lab pulse generator: **5 ns resolution, 290 ps RMS jitter, ~10 ppm stability**, achieved by hand-writing single-cycle-per-instruction loops (200 MHz, no cache/branch prediction) — *no ISA timing abstraction at all*, i.e. exactly the NOP-insertion technique PRET argues against. *For us*: a useful raw-precision lower bound, and confirms even Jane Street's own cited prior art has no deadline-style instruction.

**12. "Soft peripherals" (Ubicom IP3023, Embedded.com trade article) — general "software-defined peripheral" category.** Commercial, not open/academic: 8-way hardware-multithreaded barrel processor, one thread per cycle round-robin (64-entry task table), no caches, claimed near-nanosecond task-switch determinism; Ethernet/USB/PCI bit-banged in software. *Uncertain*: only a secondary trade article accessible, treat numbers as vendor claims. *For us*: existence proof that even wired-MAC-class protocols have been bit-banged from a deterministic multithreaded core with zero line-coding hardware and no public formal-verification story.

|---|---|---|---|---|
| PRET (2007) / Ip&Edwards deadline (2006) | `dead`/`deadi`: down-counter blocks then reloads | memory-mapped registers only | cycle-exact spacing by construction | position paper / single small prototype; no OS story |
| PTARM (CASES 2008) | deadline instr., 6-stage thread-interleaved pipeline | memory-mapped UART only | deadline exact; memory-wheel window up to 77 cyc | no serialization hardware; SPARC-only |
| FlexPRET (RTAS 2014) | `DU` delay-until (abs. ns), `EE`/`DE` exception-on-expire, HRTT/SRTT scheduler | none dedicated (RISC-V GPIO) | HRTT slot guaranteed every N cycles; idle cycles reclaimed by SRTTs | no pin/line-coding hardware; RISC-V priv. port incomplete |
| Patmos / T-CREST | none (WCET-analyzable pipe/caches); optional memory-mapped "Deadline" stall device | memory-mapped UART; **fixed EthMac block** | WCET-bounded, explicitly *not* repeatable by design | Ethernet is fixed hardware, not firmware; needs external WCET tool |
| XMOS XS1 | per-port hardware timer + `SETPT`; `SETCLK` clock blocks | ports = buffered/serializing pin interfaces w/ input conditions | port I/O exact to port clock, decoupled from thread scheduling | no CRC/line-coding hardware; proprietary; no cross-port deadline story |
| Propeller 1 | `WAITCNT D,S` (wait then accumulate, no drift); `WAITPEQ/WAITPNE` | plain shared GPIO across 8 cogs | `WAITCNT` cycle-exact | `WAITPEQ/WAITPNE` can hang forever (documented); no CRC hardware |
| Propeller 2 | smart-pin NCO/PWM/serial modes; Streamer (2-cycle deterministic) | per-pin autonomous smart hardware, closest prior art to "lanes" | smart pin free-runs off own NCO once armed | no CRC/bit-stuffing hardware; proprietary; no formal-verification literature found |
| RP2040 PIO (academic use) | fixed per-instruction cycle cost; relative wait/delay, no absolute deadline reg | state-machine GPIO w/ autopull/push FIFOs | empirically 7.5 ns / 290 ps jitter (Starkey et al. 2024) | no published formal semantics/proof (gap); 32-word shared program memory; no CRC |

## 4. Ranked novelty directions

1. **Formally verified CRC/line-coding lane fused with a proven deadline ISA.** *Novel because*: every deadline-instruction machine (PRET/PTARM/FlexPRET) has zero serialization hardware; every architecture with serialization hardware (XS1, P2 smart pins, RP2040 PIO) has zero CRC/bit-stuffing hardware and no proof tying it to the timing model. *Feasibility*: **High** — CRC hardware is already budgeted (design doc §7); the new work is proof effort, not area. *Helps*: USB and Ethernet — the two protocols nobody in the competitor landscape has working.

2. **Publish a formal ISA semantics + machine-checked timing proofs, positioned against a real literature gap.** *Novel because*: no formal-semantics/proof paper exists for RP2040 PIO, Propeller smart pins, or XS1 timed ports — only ad hoc SAT checks (BitLoom) or nothing. *Feasibility*: **High** — verification tooling (SymbiYosys, k-induction) is already planned; incremental cost is writing it up as a citable artifact. *Helps*: all protocols; directly strengthens the "novel verification methodology" criterion.

3. **ISA-wide "no permanent hang" proof for every blocking instruction.** *Novel because*: Propeller 1's datasheet documents `WAITPEQ`/`WAITPNE` can hang forever; XS1 conditions can too without a timeout; no cited architecture proves a system-wide liveness invariant that every wait eventually resolves. *Feasibility*: **High** — `WAITP` already supports an optional timeout register; the work is proof-writing, not new hardware. *Helps*: SPI/I2C slave robustness against a stuck/malicious master, and USB device mode.

4. **Per-lane hardware deadline comparators fed by the proven global timebase.** *Novel because*: XS1 gives every port its own timer but no cross-port deadline-arithmetic guarantee; PRET/FlexPRET give one CPU-level deadline register but no per-pin hardware timers. Combining them — lanes carrying their own comparator synced to shared `T` — is unclaimed. *Feasibility*: **Medium** — modest added comparator logic per lane, nontrivial extra proof obligation per lane. *Helps*: tight SPI/I2C slave timeout windows and USB bit-timing margins.

5. **On-chip cycle-timestamped pin-event trace buffer as a verification artifact, not just a debug convenience.** *Novel because*: none of the cited architectures documents an on-chip, deadline-timebase-stamped trace buffer as a first-class verification artifact for post-silicon bring-up — something judges can watch work live rather than only read about. *Feasibility*: **Medium** — needs SRAM/area budget (competes with instruction memory or reuses host-FIFO infrastructure) plus host-side tooling. *Helps*: all protocols during the hardware bring-up phase (design doc §11).

6. **Coverage-quantified, LLM-assisted property synthesis directly from the machine-readable ISA spec.** *Novel because*: no cited architecture paper discusses LLM-assisted formal-property generation at all; this turns an already-planned line item (design doc §11) into a measurable claim ("% of ISA instruction classes with a proved property"). *Feasibility*: **Medium** — no silicon cost, real engineering time; risk is schedule, not area. *Helps*: verification confidence across every protocol; most legible answer to the "AI-assisted... verification" judging language.

7. **(Stretch) A minimal two-core, shared-timebase variant as a small-scale, provable analogue of InterPRET.** *Novel because*: InterPRET does time-predictable multicore at large NoC/FPGA scale; nothing here shows a ~24K-cell, two-deadline-core design with a proved non-interference property on a shared `T` register instead of a full NoC. *Feasibility*: **Low–Medium** — already a v1/stretch idea in our design doc §12; real schedule risk in 18 weeks. *Helps*: running two protocols concurrently (e.g. UART debug console alongside SPI flash).
