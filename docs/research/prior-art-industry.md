# Prior Art: Industrial Programmable I/O Engines and Community Protocol Hacks (collected 2026-09-15)

Scope: RP2040/RP2350 PIO, TI PRU-ICSS, NXP FlexIO, ESP32 RMT/ParlIO, PSoC UDB, Propeller 2 Smart Pins, and community projects (pico-pio-usb, Pico-10BASE-T/pico_eth, can2040, PIO SWD probes, pico-rmii-ethernet, V-USB, espthernet). 28 sources opened via WebSearch/WebFetch; PDFs where WebFetch's markdown conversion failed were downloaded and text-extracted locally (pypdf) for verification against page/section numbers. Uncertain claims are flagged.

## 1. Summary

Every industrial "protocol-in-firmware" engine studied uses the same trick as our draft: split a tiny, deterministic sequencer (state machine / PLD / cog) from a small set of hardware primitives that do the fast part (shift registers, timers, CRC) so the CPU only has to think at byte granularity. None of them, however, make *timing itself* a provable, first-class ISA concept — PIO and PRU firmware still pads instruction counts by hand to keep code paths equal-length, FlexIO's timers must be pre-computed per protocol, and PSoC UDBs require schematic/Verilog PLD design rather than plain firmware. The community projects (can2040, Pico-PIO-USB, Pico-10BASE-T/pico_eth, espthernet) show exactly where PIO-class engines are pushed to their limit: NRZI/Manchester clock recovery, bit-stuffing, and bus-contention detection are all done by hand in PIO assembly or interrupt-driven C, each project independently reinventing the same tricks. That reinvention is where our design has room to add genuinely defensible, novel hardware: provable deadline scheduling, a lane-level contention/clock-stretch primitive, and hardware edge-timestamping for clock recovery.

## 2. Per-engine analysis

**RP2040/RP2350 PIO** (datasheet ch.3 / ch.11). Each PIO block runs up to 4 state machines from a shared 32-instruction, 1-write/4-read instruction memory; one instruction executes per cycle unless it stalls (e.g. `WAIT`), and any instruction can append a 0–31 cycle delay. 9 opcodes (`JMP WAIT IN OUT PUSH PULL MOV IRQ SET`). Side-set drives extra GPIOs as a side effect of any instruction, unaffected by stalls. Each SM has a 16.8 fixed-point clock divider and a pair of 4-word FIFOs (joinable to 8 words via `FJOIN`) with dedicated DREQ lines for DMA. 8 IRQ flags synchronize SMs with zero delay penalty. **RP2350 changes** (§11.1.1, verified against datasheet text): PIO version register; `GPIOBASE` addresses any 32 of >32 GPIOs; `CTRL.NEXT_PIO_MASK`/`PREV_PIO_MASK` start/stop/sync SMs across neighboring blocks; `IN_COUNT` masks unused `PINS` bits; both IRQ enable registers now expose all 8 SM IRQs; indexed random read/write into RX FIFO storage (`FJOIN_RX_GET/PUT`) for status/control registers; 3 blocks (12 SMs) vs RP2040's 2 (8 SMs); 1 cycle less DREQ latency. Pain point: the 32-instruction limit forces hand-balanced branch lengths for constant timing — no formal proof that two paths take equal cycles. **What it means for us**: our delay-slot branches and static-latency rule solve the same problem PIO solves by manual cycle-counting — a *provable* static-timing rule beats PIO's informal convention.

**TI PRU-ICSS** (AM335x Reference Guide SPRUHF8A). Two 32-bit RISC PRU cores at 200 MHz, one instruction per cycle, pins mapped directly into registers R30 (output) and R31 (input) — a write to R30 appears on the pin one cycle later (~5 ns). Enhanced GPIO adds hardware modes beyond raw register writes: 16-bit parallel capture, 28-bit serial shift-in, ping-pong 16-bit serial shift-out (shadow registers, `LOAD_GPO_SH0/1`, `ENABLE_SHIFT`) clocked by two cascaded dividers off the 200 MHz clock — a built-in UART/shift-register lane. A dedicated MII_RT module with two MII ports feeds Ethernet frame data to the PRUs; ICSS EMAC firmware implements a 2-port 10/100 Mbps MAC or cut-through switch via a round-robin "Micro Scheduler" of firmware tasks (TI wiki dev guide). Pain point: everything beyond raw R30/R31 bit-banging is a fixed peripheral the firmware configures, not something the ISA expresses generically — no equivalent of PIO's autopull/autopush or our lane crossbar. **What it means for us**: PRU proves 200 MHz single-cycle GPIO plus a purpose-built shift/MII block is enough for a full Ethernet MAC; our lanes at 50 MHz need richer line coding to make up for 4x less clock.

**NXP FlexIO** (AN5034, AN12780, AN5133, extracted directly). A cross-bar of shifters and timers, not a sequencer: FlexIO has no instructions at all. UART uses 1 timer + 1 shifter + 1 pin per direction; SPI uses 2 timers (one for SCK, one for CS + shift/load control) + 2 shifters + 4 pins; I2C master uses 2 timers (SCL generation, shift control) + 2 shifters, with open-drain done via output-enable rather than driving high. Confirmed pain point directly from AN5133: "the I2C features such as multi-master/arbitration, handshaking, and clock stretching are not supported" in this reference implementation. **What it means for us**: FlexIO's timer+shifter model is close to our lane concept but fixed-function per protocol (no programmable line coding, no CRC); its explicit admission that clock stretching/arbitration are unsupported is a concrete, citable gap our lane's `WAITP`-with-timeout primitive already targets.

**ESP32 RMT / ESP32-P4 ParlIO.** RMT is symbol-based, not instruction-based: each `rmt_symbol_word_t` is a (15-bit duration, level) pair generated/consumed by software encoders; per-channel memory is a minimum of 64 symbols (or a DMA ring, e.g. 1024 symbols) and TX/RX are separate channels with independent clock dividers, optional carrier modulation, and hardware looping. Documented limitation: RMT segregates TX/RX into separate channels, so bidirectional, arbitrated protocols like I2C are awkward. ParlIO (ESP32-P4) is a parallel bus engine (up to 8/16 data lines + 1-2 clocks per direction, DMA-backed) aimed at LCD/camera/LED-matrix use, not serial protocol emulation. **What it means for us**: RMT's symbol memory is a reasonable model for our per-lane shift buffer, but its TX/RX split is a structural reason RMT is not proposed as I2C/SPI hardware by Espressif — our lane's ability to reconfigure direction and pin ownership per instruction avoids that split.

**Cypress/Infineon PSoC UDB** (UDB Editor Guide, extracted directly). A UDB pairs an 8-bit "Datapath" ALU (with two 8-bit × 4-deep FIFOs, 8 user-defined instructions) with two 12C4 PLD blocks used to build a controlling state machine; UART/SPI/I2C "Components" in PSoC Creator are pre-built UDB configurations chained together. Pain point, confirmed in the guide: designing new behavior means using the UDB Editor / Verilog / "Datapath Configuration Tool," i.e. hardware design, not firmware — directly contradicting the brief's "protocols as firmware" goal. **What it means for us**: UDB is the clearest illustration of alternative B in our own design doc (fixed logic blocks) losing to alternative C (time-triggered core + lanes) — UDB protocols are hardware-synthesized per design, ours are loaded post-fabrication.

**Parallax Propeller 2 Smart Pins.** 64 smart I/O pins, each with 4 shared 32-bit registers (Mode, X, Y, Z) configured by `WRPIN`, supporting async serial TX/RX up to clock/3 baud and sync serial up to clock/2, plus community "objects" claiming UART/SPI/I2C/CAN/USB modes *(per Elektor's write-up and Parallax spec sheet; full modes table not independently verified — uncertain)*. 8 cogs at up to 320 MHz (8×160 MIPS) drive the pins. **What it means for us**: P2's clock/2–clock/3 smart-pin baud limits are roughly analogous to our lane's fractional clock divider; the "many small autonomous pins, no crossbar to a central protocol brain" model is close to PIO/lanes but without our shared timebase `T` for drift-free multi-pin synchronization.

## 3. Community projects at the limit

- **pico-pio-usb** (sekigon-gonnoc). LS/FS host+device on RP2040 PIO: 1 PIO block, 3 SMs, 32 instructions; needs a 1 ms repeating timer (host) and a PIO IRQ (device RX); external 1.5 kΩ D+ pull-up required. NRZI/bit-stuffing/clock-recovery details live in source, not README (not independently verified). https://github.com/sekigon-gonnoc/Pico-PIO-USB/blob/main/README.md
- **Pico-10BASE-T** (kingyoPiyo). TX-only 10BASE-T from 2 GPIOs through two 47 Ω + one 470 Ω resistors (DAC-style Manchester); explicitly TX-only, warns not to connect to PoE equipment. https://github.com/kingyoPiyo/Pico-10BASE-T
- **pico_eth** (holysnippet, bidirectional 10BASE-T). Requires system clock of exactly 120 or 240 MHz "because of the fractional divisor of the PIO clock"; 1 PIO block, 4 DMA channels, 2 IRQs, 3 GPIOs; RX uses a passive resistor divider (~0.45×Vcc bias), no comparator; author notes RX still has no NLP (link-pulse) detection. https://github.com/holysnippet/pico_eth_doc
- **can2040** (Kevin O'Connor). CAN 2.0B up to 1 Mbit/s, one PIO block, all 4 SMs; fixed 32 PIO cycles/bit, latched at cycle 0, sampled at cycle 24; arbitration detected in PIO assembly (`jmp pin nextbit`/fall-through-to-collision); stuffing/CRC done in the C driver, not PIO. Limits: permanently "error-passive" (no auto bus-off); interrupt latency above ~80 bit-times can permanently lose messages. https://github.com/KevinOConnor/can2040/blob/master/docs/Features.md, https://vanhunteradams.com/Pico/CAN/CAN.html
- **pico-rmii-ethernet** (sandeepmistry). 100 Mbit RMII MAC on PIO+DMA+dual-core; RP2040 deliberately underclocked to 50 MHz to match the RMII reference clock; documented issue that 100 Mbps is unstable while 10 Mbps works. https://github.com/sandeepmistry/pico-rmii-ethernet
- **PIO SWD/JTAG probes**. Basic PIO SWD is "read N bits / write N bits" per instruction; community reports of a 150 MHz sys-clock `/3` PIO divider reaching 25 MHz SWD, above the RP2040 datasheet's 24 MHz recommendation *(secondary source, uncertain)*. Professional tracing (ORBTrace) abandons PIO entirely for an FPGA running CMSIS-DAP "natively in gateware" since trace data can approach 200 Mbps — a real ceiling for software/PIO probes. https://github.com/raspberrypi/debugprobe, https://hackaday.com/2022/07/26/orbtrace-effort-open-tool-for-professional-debugging/
- **V-USB** (obdev.at). Firmware-only USB 1.1 LS device on any AVR ≥12 MHz; NRZI + bit-stuffing done in real time in the interrupt path, not buffered; only 2–3 I/O pins; explicitly non-compliant on error handling/electrical spec. https://www.obdev.at/vusb/
- **espthernet** (cnlohr). Full-duplex 10BASE-T on ESP8266's I2S peripheral at 40 MHz oversampling; incoming signal "absolutely must" be DC-biased toward 0 for reliable slicing; author hand-tuned the Manchester decode table against captured traffic since a general algorithm was "almost impossible"; calls the result "relatively unreliable and coincidentally functional." https://github.com/cnlohr/espthernet

## 5. Ranked improvements over PIO/PRU (novelty candidates)

1. **Formally-proved zero-jitter deadline scheduling** (spec §6 properties). *High* — SymbiYosys is already in the toolchain; properties are small, local register compares. Unlocks all protocols, especially where PIO/PRU/FlexIO programmers today hand-verify equal-length code paths (UART bit loops; 10BASE-T's 16±8 ms link-pulse spacing, where drift compounds over minutes). No engine studied claims a formal jitter proof.
2. **Lane-level bus-contention / clock-stretch primitive** (compares driven vs. sampled pin every cycle, raises a `WAITF`-visible flag). *High* — reuses existing `IN`/pin-sync hardware. Unlocks I2C clock stretching and multi-master arbitration (explicitly unsupported per NXP AN5133) and CAN arbitration (hand-coded in can2040's PIO assembly as `jmp pin nextbit`/fall-through-to-collision). At 50 MHz, 1 Mbit CAN gets 50 cycles/bit oversampling — better margin than can2040's 32.
3. **Programmable bit-stuffing/destuffing + CRC lane** (already scoped, spec §7). *Medium* — CRC alone is easy; general NRZI stuffing (USB) *and* CAN stuffing in the same hardware, verified for 3 protocols, is real scope risk in 18 weeks. Unlocks USB-LS (bit-stuffing every ≤6 ones; 1.5 Mbit/s = 33.3 core cycles/bit at 50 MHz, generous), CAN stuffing, 10BASE-T FCS (CRC-32) — all currently done by hand in can2040's C driver and V-USB's assembly.
4. **Hardware edge-timestamp capture for clock recovery** (on pin edge, latch `T` into a small FIFO instead of core polling). *Medium* — natural extension of the lane + timebase, needs careful FIFO/overrun semantics. Unlocks USB RX bit recovery, CAN RX resync-on-edge, and 10BASE-T RX — the hardest problem named by every community project studied (espthernet's hand-tuned decode table, pico_eth's missing NLP detection, can2040's edge-search-window constants).
5. **On-chip protocol trace/logic-analyzer ring buffer**, exposed over the host SPI port. *Medium/Low* — competes for the same SRAM budget as instruction memory; a flip-flop-only fallback (last N events) is safer. Unlocks nothing protocol-specific but directly serves the "novel verification methodologies" judging criterion, which no engine studied addresses in silicon.
6. **Native RMII lane at 50 MHz for 100BASE-TX**, beyond the brief's 10BASE-T stretch goal. *Medium-Low* — RMII's reference clock is exactly 50 MHz carrying 2 data bits/clock, matching our core clock (pico-rmii-ethernet deliberately underclocks an RP2040 to 50 MHz for the same reason, and still only gets 10 Mbps stable); real risk is external PHY dependency, pin budget, and CRC-32/preamble handling in 18 weeks. Unlocks 100 Mbit Ethernet, beyond any competitor repo found.
7. **Two cores sharing instruction memory** for independent concurrent protocols (open v1 idea, spec §12). *Low priority* — PIO already offers 8–12 concurrent SMs and PRU ships two full cores, so this is the least differentiated item here; worth pursuing only after 1–5 are solid.
