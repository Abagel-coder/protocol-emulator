# Verification Methodology Research — Novelty Scan (2026-09-15)

Scope: what verification approaches are both credible and novel for the "time-triggered core + programmable lanes" protocol-emulator ASIC (see `competition-brief.md` and `docs/superpowers/specs/2026-09-15-protocol-emulator-design.md`), for a 1–2 person, 18-week entry to the Jane Street ASIC competition. Sources were opened via web search/fetch on 2026-09-15; all URLs below were actually retrieved (full fetch or a search result that returned genuine page content), not guessed. Tool versions and paper claims should be re-checked close to submission.

## 1. Summary

The strongest, cheapest "novel methodology" story combines three well-precedented-but-rarely-combined techniques: (1) machine-checked, k-induction-provable timing properties for the deterministic core — a natural fit since "every instruction's latency is a function of its opcode only" is exactly the property shape SymbiYosys and riscv-formal-style RVFI harnesses handle (methodology transfers even though the ISA isn't RISC-V); (2) mutation-tested (MCY) differential/constrained-random testing against a Python reference model generated from the same ISA YAML that drives the assembler, closing the "how do we know the testbench would catch a bug" gap most competition entries leave open; and (3) AI-assisted verification framed narrowly and evidentially — LLM-drafted SVA/stimuli/adversarial firmware, checked in with prompts and measured against the mutation/coverage baseline, not asserted as "we used AI." The literature (AssertLLM, LLM4DV, FLAG, GateTruth, "Revolution or Hype?") agrees: LLMs accelerate drafting but aren't trustworthy alone, and judges will discount unmeasured AI claims — so the differentiator is turning AI assistance into numbers (bug-finding rate, mutation-score delta, coverage-closure time), not narrative.

## 2. Technique catalogue

**1. riscv-formal-style RVFI/property harness (custom ISA, not RISC-V)** — Not riscv-formal itself (RV32I/RV64I-specific, explicitly "work in progress," no retargeting story), but its *pattern* — a formal interface exposing "did instruction X retire, with what operands, in what cycle" plus one SBY property file per instruction class — is directly reusable. Tools: SymbiYosys + Yosys, free (OSS CAD Suite). Maturity: riscv-formal is mature, used on real cores (PicoRV32); an equivalent harness for a 16-bit custom ISA is mechanical but from-scratch. Effort: ~5–8 days. Evidence: a table of "N instruction classes, M properties, unbounded or K-cycle bounded," plus checked-in `.sby` files. Sources: [YosysHQ/riscv-formal](https://github.com/YosysHQ/riscv-formal), [RISC-V Formal docs](https://riscv-formal.readthedocs.io/), [RISC-V International blog](https://riscv.org/blog/from-simulation-bottlenecks-to-formal-confidence-leveraging-formal-for-exhaustive-risc-v-verification/) (a real IBEX `BLT` bug formal caught that simulation missed).

**2. SymbiYosys BMC + k-induction on the timing properties in spec §6** — SBY supports BMC, unbounded (k-induction) proof, cover-mode testbench generation, and liveness, via smtbmc/btor/aiger/abc engines and open solvers (Yices2, Boolector, Z3, Bitwuzla). Maturity: high, YosysHQ-maintained, already in the team's toolchain. Effort: 3–5 days for the 5 properties already listed in the design doc (`WAITT` exactness, static per-cycle PC advance, `uio_oe` reset safety, single pin-write-per-cycle, FIFO no-loss/no-dup). Evidence: proof logs + a "properties proved, engine, wall-clock time" table. Sources: [SymbiYosys docs](https://symbiyosys.readthedocs.io/), [Clifford Wolf's SBY/yosys-smtbmc talk](http://www.testandverification.com/wp-content/uploads/2017/Formal_Verification/Clifford_Wolf.pdf).

**3. vibe-pio-style formal model of the pin engines ("lanes")** — Close precedent: a cycle-accurate, formally-verifiable Verilog model of the RP2350 PIO block (a similar "programmable state machine feeding pins" component), built with only Icarus + Yosys + SymbiYosys, spec-conformance monitors embedded in RTL, traceability back to the datasheet, disclosed AI assistance (commits carry "Agent:" trailers). A template for verifying this design's lane/crossbar block. Effort: 4–6 days. Evidence: reproducible container, spec-source traceability file, proof logs. Source: [kristofferkoch/vibe-pio](https://github.com/kristofferkoch/vibe-pio).

**4. EQY (Yosys equivalence checking) — RTL vs. gate-level, pre/post-refactor** — Partitions the design and checks matching points independently, scaling better than a single SBY miter proof; used for "did synthesis/LibreLane change behavior" and "did a refactor stay safe." Maturity: actively maintained, free (OSS CAD Suite). Effort: 1–3 days once a gate-level netlist exists (fits the TT template's `GATES=yes` flow). Evidence: "RTL and post-LibreLane netlist proved equivalent." Sources: [EQY docs](https://yosyshq.readthedocs.io/projects/eqy/en/latest/), [EQY GitHub](https://github.com/YosysHQ/eqy).

**5. MCY (Mutation Cover with Yosys) mutation-score for the cocotb testbench** — Generates thousands of netlist mutations, formally filters out those that can't affect outputs, reports the percentage the suite actually kills, with a GUI/dashboard for blind spots. Maturity: mature, YosysHQ-maintained. Effort: 3–5 days for baseline, plus ongoing gap-closing. Evidence: "testbench kills N% of surviving mutants" — quantified rigor a judge can check, and something most competitors won't report (see #10). Sources: [MCY README](https://github.com/YosysHQ/mcy/blob/main/README.md), [MCY methodology docs](https://yosyshq.readthedocs.io/projects/mcy/en/latest/methodology.html).

**6. Single-source ISA description → assembler + Python model + RTL decode constants + docs (Sail-inspired, not Sail itself)** — Full Sail (official RISC-V spec) generates C/OCaml emulators, theorem-prover definitions, and coverage-instrumented test generators from one spec — but the real toolchain is disproportionate for a 16-bit custom ISA ("significant engineering effort beyond basic ISA specification"). The right-sized version is design principle 5 already in the spec: one YAML, generating the assembler, a Python differential-testing model, Verilog decode constants, and docs. Effort: 4–6 days (mostly already planned). Evidence: "assembler, simulator and RTL decoder provably come from one file, diffed in CI" — distinct from what listed competitors currently do. Sources: [sail-riscv GitHub](https://github.com/riscv/sail-riscv), [Sail POPL'19 paper](https://www.cl.cam.ac.uk/~pes20/sail/sail-popl2019.pdf).

**7. cocotb-coverage — constrained-random + functional coverage** — `Randomized`/constraint classes plus `@CoverPoint`/`@CoverCross`, coverage export to XML/YAML with merge across regressions. Actively maintained (v2.0, Oct 2025, cocotb ≥2.0). Effort: 2–4 days to instrument opcode/wait/lane-mode coverage per the design's own "differential" verification-plan row. Evidence: a coverage report closing opcode × wait-mode × lane-mode cross bins. Source: [cocotb-coverage GitHub](https://github.com/mciepluc/cocotb-coverage).

**8. pyuvm — full UVM-in-Python on cocotb** — Implements most of IEEE 1800.2 (factory, phasing, TLM, sequences/sequencers, RAL). Actively maintained. Verdict: probably *not* worth it for a 1–2 person team — UVM/RAL overhead is disproportionate to one small core; cocotb-coverage alone covers the need with less boilerplate. Included to justify *not* choosing it. Source: [pyuvm GitHub](https://github.com/pyuvm/pyuvm).

**9. Protocol-timing-tolerance differential testing against Python reference models** — Already precedented by the closest competitor, BitLoom: independent Python re-implementations of UART/SPI/I2C/WS2812/Manchester driven through the real host interface, constrained-random dividers/payloads, explicit negative testing (framing errors, NACK, glitch filter threshold), plus small Yosys-SAT FIFO proofs (24-cycle bounded). Validates the general approach but isn't itself a differentiator since a competitor already ships it — the edge has to be formally proved (unbounded) timing tolerances and mutation-scored testbenches, which BitLoom doesn't report. Source: [sheehanmunim/bitloom](https://github.com/sheehanmunim/bitloom).

**10. Mutation testing as meta-evidence for any AI-generated or AI-assisted test artifact** — GateTruth (mutation-testing audit of RTL-generation benchmarks) found 46/60 tasks on an internal suite hit ≥95% mutation-kill, but 72% of 46 auditable RTLLM v2.0 designs scored *below* 95% (three at 0%) — most "tests pass" claims in this space are unaudited and often hollow. The same paper found a silent 4,096-token output cap had been truncating model outputs and skewing a leaderboard until raised to 16,384. Strong evidence that mutation score, not "tests pass"/coverage %, is the credible metric, plus a reproducibility cautionary tale. Source: [GateTruth (arXiv 2608.12635)](https://arxiv.org/abs/2608.12635).

**11. AssertLLM — multi-LLM pipeline for spec → SVA** — Three-stage pipeline (structural-spec extraction → signal mapping → assertion generation), evaluated on one full design (23 I/O signals): 89% of generated assertions syntactically and functionally correct. Useful for drafting host-SPI/FIFO/handshake assertions from spec prose; the 11% error rate means every generated assertion still needs human/formal review. Source: [AssertLLM (arXiv 2402.00386)](https://arxiv.org/abs/2402.00386).

**12. LLM4DV — LLM-orchestrated stimulus generation vs. constrained-random** — Open-source framework; six LLMs × six prompting strategies over eight designs; authors report 98.94% coverage on a data prefetcher, 86.19% on an instruction decoder, and outperforming constrained-random on a complex CPU (author-reported, not independently reproduced). Useful for seeding corner-case programs for the wait/lane classes, but numbers are design-specific — re-measure rather than quote. Source: [LLM4DV (arXiv 2310.04535)](https://arxiv.org/abs/2310.04535).

**13. AutoSVA — non-LLM automatic FV-testbench generation for module interfaces** — Older (2021), template/interface-driven generator of liveness/safety FV testbenches for control-logic module boundaries (e.g., FIFO/handshake interfaces), evaluated on deadlock-critical modules of real open-source hardware. Conceptually useful for the host-FIFO/lane-handshake property in spec §6 item 5; check current maintenance before depending on the tool itself. Source: [AutoSVA (arXiv 2104.04003)](https://arxiv.org/abs/2104.04003).

**14. FLAG — grammar + formal filtering + LLM for protocol SVA from informal docs** — Two-stage: grammar-template candidates, then formal (timing-diagram) filtering that the paper reports keeps only 5–22% of candidates before an LLM does final natural-language cross-checking. Core finding — "the hard part is extracting the right information from unstructured, ambiguous documents, not English→SVA translation" — applies directly to writing SPI/I2C/UART assertions from datasheet prose. Source: [FLAG (arXiv 2504.17226)](https://arxiv.org/abs/2504.17226).

**15. microcotb — hardware-in-the-loop, same test suite on real silicon** — A micro-reimplementation of cocotb running the *same* `@cocotb.test()` files against an RP2040 (MicroPython), a Raspberry Pi 5, an FPGA via USB bridge, or a Tiny Tapeout demoboard instead of a simulator — built explicitly for TT post-silicon testing. ~250× slower than desktop simulation, so it's for functional confirmation, not regression scale. Effort: 2–4 days for a thin hardware DUT adapter once the cocotb testbench exists (it will, per the verification plan). Evidence: "the identical test file that ran pre-tapeout simulation also ran, unmodified, against the physical chip." Source: [psychogenic/microcotb](https://github.com/psychogenic/microcotb).

## 3. Ranked adoption list (novelty × credibility / effort)

1. **SymbiYosys k-induction proofs of the ISA's static-timing guarantee.** *Claim:* "We formally prove, not merely test, that every non-wait instruction advances the PC in exactly one cycle and that `WAITT` releases on the exact tick — the ISA's core timing promise is a machine-checked theorem, not an empirical observation." *Artifacts:* SBY property files for spec §6 items 1–2, proof logs, wall-clock/engine table checked into `verification/formal/`.

2. **Reset-safety and pin-driver formal properties (bidirectional pin/`uio_oe` safety).** *Claim:* "We prove `uio_oe == 0` from reset until the first `OE` instruction, and that any pin output register changes at most once per cycle and only via an executed pin/lane op — a chip that can never glitch a bus it doesn't own, proved rather than hoped." *Artifacts:* SBY properties for spec §6 items 3–4, covering exactly the "safe by default" design principle.

3. **MCY mutation score reported for the whole cocotb+differential test suite.** *Claim:* "Our testbench isn't just passing — it kills N% of formally-filtered netlist mutants, measured with the same tool (MCY) that a recent academic audit (GateTruth) found most RTL benchmarks fail to clear." *Artifacts:* `config.mcy`, mutation database, coverage-gap list with follow-up fixes, before/after mutation-score if AI-suggested tests are added (ties into pitfall-avoidance below).

4. **microcotb hardware-in-the-loop replay of the exact simulation testbench on the fabricated chip / FPGA breakout.** *Claim:* "The same cocotb test files that ran against RTL and gate-level simulation, unmodified, also ran against the physical demoboard and FPGA breakout — closing the loop from formal proof to silicon with one test suite instead of three." *Artifacts:* microcotb DUT adapter, a CI-style log showing identical test IDs passing in sim, gate-level sim, and hardware.

5. **vibe-pio-style formal spec-conformance model for the pin-engine/lane block, with datasheet traceability.** *Claim:* "Each lane's line-coding and CRC behavior is checked against a property derived and traced line-by-line back to the protocol timing tolerance table (USB/Ethernet bit timing), following the same open-tool pattern used to formally verify the RP2350 PIO block." *Artifacts:* `spec-sources.md`-style traceability file mapping lane properties to protocol datasheet clauses, SBY proofs for lane/crossbar timing.

6. **Single-source ISA generator with a CI diff-check ("assembler/model/RTL/docs can't drift").** *Claim:* "The assembler, the Python differential-testing model, the RTL opcode decode table, and the instruction documentation are all generated from one YAML file; CI fails if any generated artifact is stale relative to the source." *Artifacts:* the generator script, a CI job that re-generates and diffs, one paragraph in the write-up citing the Sail precedent as prior art for why single-source ISA definitions are considered best practice at the architecture-standardization level.

7. **cocotb-coverage functional coverage over opcode × wait-mode × lane-mode with closure evidence.** *Claim:* "Constrained-random firmware exercises every opcode class crossed with every wait/lane mode; functional coverage (not just line coverage) closes to X% before tapeout, tracked with cocotb-coverage's `CoverCross`." *Artifacts:* coverage database + closure-over-time plot.

8. **EQY RTL-vs-gate-level equivalence check post-LibreLane, as a tapeout gate.** *Claim:* "Before submitting the GDS, we formally proved the LibreLane-synthesized gate-level netlist equivalent to the RTL that was formally and mutation-tested — synthesis can't have silently changed behavior." *Artifacts:* `.eqy` file + pass log, wired into the same CI that runs `make GATES=yes`.

## 4. Pitfalls: AI-assisted claims judges will discount, and how to make them rigorous

- **Bare "we used AI to help verify" claims are close to worthless.** The literature is explicit that LLMs "remain inherently probabilistic and prone to hallucinations" and unaided LLM bug detection "often suffer[s] from high false positive rates" requiring human validation (corroborated by AssertLLM's 89%-not-100% accuracy and LLM4DV's need for extra "prompting improvements"). **Fix:** never claim AI verified something; claim AI *drafted* an artifact later checked by a deterministic tool (SymbiYosys, MCY, EQY) or a human, and report the acceptance rate.
- **Unmeasured coverage/pass-rate claims.** GateTruth found most RTLLM v2.0 designs it audited scored under 95% mutation-kill despite reporting passing tests, and a hidden 4,096-token truncation had silently corrupted an earlier leaderboard — "tests pass"/"coverage is high" are not self-verifying. **Fix:** report mutation score (MCY) alongside any coverage percentage, split by author (human vs. LLM-suggested) so AI's incremental contribution is separately auditable.
- **Non-reproducible AI usage.** Check in the prompt, model/version, and the draft-vs.-accepted diff for any LLM-assisted assertion, stimulus, or adversarial firmware — the design doc already commits to this ("checked in with the prompt and the outcome"). This is standard reproducibility practice, not a hardware-specific idea, but it applies directly here.
- **Conflating LLM-authored code with LLM-authored *proof*.** A property an LLM drafts isn't evidence until SymbiYosys/MCY/a formally-filtered mutation run checks it; FLAG's pipeline treats its LLM stage as a filter *after* formal timing-diagram checking, not the source of truth — mirror that ordering.
- **Claiming novelty for things a competitor already ships.** BitLoom already does Python-reference-model differential testing, constrained-random dividers, and bounded Yosys-SAT FIFO proofs, so "constrained-random against a reference model" alone won't read as novel. The edge is what BitLoom doesn't report: mutation score, unbounded k-induction rather than 24-cycle-bounded SAT, and hardware-in-the-loop replay of the same suite.
- **Formal-verification overclaiming.** Scope "formally verified" precisely (which properties, bounded vs. unbounded, what was assumed) — riscv-formal's own README still says "work in progress" after years of real-core use, and IBEX's BLT bug (caught by formal, missed by simulation) illustrates formal's value without proving it suffices alone; pair every formal claim with what simulation/mutation testing separately caught.
